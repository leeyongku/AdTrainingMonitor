# "대원 추가" / "비밀번호 재설정" / "대원 정보 수정" 기능 만들기 — 초보자용 단계별 가이드

이 문서는 `AdTrainingMonitor` 앱의 **대원 목록 화면**에서 다음 세 가지 관리자 기능을
처음부터 끝까지 직접 만들어 볼 수 있도록 정리한 가이드입니다.
안드로이드/Kotlin, ASP.NET Core가 처음이어도 순서대로 따라 하면 완성할 수 있습니다.

- **파트 A. 대원 추가** — 목록에 이미 그려져 있던 "대원 추가" 버튼을 실제로 동작하게 만들기 (백엔드 + 안드로이드 모두 수정)
- **파트 B. 비밀번호 재설정** — 대원 항목을 클릭하면 새 비밀번호를 입력받아 서버에 반영하는 기능 새로 만들기 (백엔드 + 안드로이드 모두 수정)
- **파트 C. 대원 정보 수정** — 목록의 연필 아이콘으로 이름/계급/소속 부대/얼굴 사진을 나중에 고치는 기능 새로 만들기 (백엔드 + 안드로이드 모두 수정)

세 기능 모두 "관리자가 대원을 직접 관리한다"는 이 앱의 기존 패턴
(`createMember`, `deactivateMember`)을 그대로 따릅니다.

> **아키텍처 참고 (MVVM)**: 이 앱의 모든 화면은 Fragment/Activity(View)와
> ViewModel로 역할이 나뉘어 있습니다. Fragment는 "화면을 그리고 사용자
> 입력을 받는" 역할만 하고, 서버 통신(Retrofit 호출)과 상태 보관(목록 데이터,
> 로딩 결과 등)은 화면마다 대응하는 ViewModel(`MemberListViewModel` 등)이
> 담당합니다. Fragment는 ViewModel이 노출하는 LiveData를 관찰(observe)해서
> 화면(RecyclerView, Toast 등)을 갱신할 뿐, 직접 `RetrofitClient`를 호출하거나
> `Toast.makeText(...)`를 호출하지 않습니다. 이 문서의 모든 코드 예시는 이
> 구조를 기준으로 합니다.

# 파트 A. 대원 추가 기능

## 1. 무엇을 만드는가

`app/src/main/res/layout/fragment_member_list.xml` 레이아웃에는 이미
"대원 추가"라는 이름의 버튼(FAB, Floating Action Button)이 그려져 있습니다.

```xml
<!-- 대원 추가 버튼 -->
<com.google.android.material.floatingactionbutton.ExtendedFloatingActionButton
    android:id="@+id/fabAddMember"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:layout_gravity="end"
    android:layout_margin="16dp"
    android:text="대원 추가"
    app:icon="@android:drawable/ic_input_add"/>
```

문제는 **이 버튼을 눌러도 아무 일도 일어나지 않는다**는 것입니다.
버튼은 화면에 그려져 있지만(레이아웃 XML), "누르면 무엇을 할지"를 정하는
코드(Kotlin의 클릭 리스너)가 연결되어 있지 않기 때문입니다.

우리가 할 일은 3가지입니다.

1. 군번/이름/비밀번호/계급/소속 부대(모두 필수)와 얼굴 사진(선택)을 입력받는
   **입력 다이얼로그(팝업창)** 만들기
2. 버튼을 눌렀을 때 그 다이얼로그를 띄우고, 입력값을 서버로 전송하는 **코드 연결**하기
3. 계급·소속 부대를 필수로 검증하고 얼굴 사진을 저장할 수 있도록 **백엔드 API도 함께 수정**하기

> 서버(백엔드)에 대원을 등록하는 API(`POST /api/members`) 자체는 이미 있지만,
> **계급/소속 부대를 필수로 검증하는 로직과 얼굴 사진을 저장하는 컬럼은 아직 없습니다.**
> 안드로이드 쪽에도 그 API를 호출하기 위한 `ApiService.createMember()`와
> `CreateMemberRequest` DTO가 이미 준비되어 있지만, 마찬가지로 사진 필드는 추가해야 합니다.
> 그래서 이번 작업은 **백엔드(Step 0)와 안드로이드 화면(UI) 코드를 함께 수정**합니다.

`app/src/main/java/com/training/monitor/data/model/Dtos.kt` 안에 아래 데이터 클래스가 있어야 합니다.

```kotlin
data class CreateMemberRequest(
    @SerializedName("military_id") val militaryId: String,
    val name: String,
    val password: String,
    val rank: String,
    // 어느 부대 소속으로 등록할지. 계급과 마찬가지로 필수.
    @SerializedName("unit_id") val unitId: Long,
    // 얼굴 사진 (Base64, JPEG, 선택). MemberListViewModel.createMember()가 인코딩해서 채워 넣는다.
    @SerializedName("photo_base64") val photoBase64: String? = null
)
```

이 6개의 필드(군번, 이름, 비밀번호, 계급, 소속 부대 ID, 얼굴 사진)가 바로 우리가 만들
입력 다이얼로그에서 사용자에게 입력받아야 하는 값들입니다. 계급/소속 부대는 필수라서
`String?`/`Long?`이 아니라 `String`/`Long`(non-null)이고, 얼굴 사진만 선택이라 `null`을
기본값으로 둔 `String?`입니다.

> 만약 위 두 가지가 프로젝트에 없다면, 이 가이드를 따라 하기 전에 먼저 추가해야 합니다.
> (이 프로젝트에는 이미 존재하므로 별도 작업이 필요 없습니다.)

## 3. Step 0 — 백엔드: 필수 검증 + 얼굴 사진 컬럼 추가하기

안드로이드 화면을 만들기 전에, 서버(백엔드) 쪽부터 손봅니다. 지금 API는 계급/소속
부대를 안 보내도 그냥 통과시키고, 사진을 저장할 자리도 없기 때문입니다.

**파일 위치**: `TrainingMonitor/Models/Entities.cs` — `User` 엔티티에 사진 컬럼 추가

```csharp
public DateTime? LastLoginAt { get; set; }

// 얼굴 사진 (선택, JPEG 바이너리 그대로 저장 — 목록 아이콘 표시용으로 작게 압축해서 올라온다)
public byte[]? PhotoData { get; set; }
```

엔티티 클래스를 수정했다면, 실제 DB 스키마에도 반영해야 합니다. 프로젝트 루트
(`TrainingMonitor` 폴더)에서 마이그레이션을 생성합니다.

```bash
dotnet ef migrations add AddMemberPhoto
```

서버를 다시 실행(`dotnet run`)하면 시작 시점에 자동으로 마이그레이션이 적용되어
DB에 `photo_data` 컬럼이 생깁니다.

**파일 위치**: `TrainingMonitor/Controllers/MembersController.cs` — 필수 검증 + 사진 디코딩

```csharp
public record MemberDto(long Id, string MilitaryId, string Name, string? Rank, string? UnitName, string Role, string? PhotoBase64);

[HttpPost]
public async Task<IActionResult> CreateMember([FromBody] CreateMemberRequest req)
{
    if (string.IsNullOrWhiteSpace(req.Rank) || req.UnitId is null)
        return BadRequest("계급과 소속 부대는 필수입니다.");

    if (await db.Users.AnyAsync(u => u.MilitaryId == req.MilitaryId))
        return Conflict("이미 등록된 군번입니다.");

    byte[]? photo = null;
    if (req.PhotoBase64 is not null)
    {
        try
        {
            photo = Convert.FromBase64String(req.PhotoBase64);
        }
        catch (FormatException)
        {
            // Base64 디코딩 실패 = 클라이언트가 보낸 사진 데이터가 손상되었거나 형식이 틀림
            return BadRequest("잘못된 사진 데이터입니다.");
        }
    }

    var user = new TrainingMonitor.Models.Entities.User
    {
        MilitaryId = req.MilitaryId,
        Name = req.Name,
        Rank = req.Rank,
        Role = TrainingMonitor.Models.Entities.UserRole.MEMBER,
        UnitId = req.UnitId,
        PasswordHash = BCrypt.Net.BCrypt.HashPassword(req.Password),
        MustChangePassword = true,
        PhotoData = photo
    };

    db.Users.Add(user);
    await db.SaveChangesAsync();
    return CreatedAtAction(nameof(GetMembers), new { id = user.Id }, null);
}

public record CreateMemberRequest(
    string MilitaryId,
    string Name,
    string Password,
    string? Rank,
    long? UnitId,
    string? PhotoBase64
);
```

목록 조회(`GetMembers`)에서도 저장된 사진을 Base64로 함께 내려주도록 수정합니다.

```csharp
return Ok(members.Select(u => new MemberDto(
    u.Id, u.MilitaryId, u.Name, u.Rank,
    u.UnitId.HasValue && unitPaths.TryGetValue(u.UnitId.Value, out var path) ? path : null,
    u.Role.ToString(),
    u.PhotoData is null ? null : Convert.ToBase64String(u.PhotoData)
)).ToList());
```

### 이 코드가 하는 일

| 코드 | 설명 |
|---|---|
| `string.IsNullOrWhiteSpace(req.Rank) \|\| req.UnitId is null` | 계급이 빈 문자열/공백/null이거나 소속 부대 id가 없으면 요청 자체를 `400 BadRequest`로 거부합니다. 이 검사를 **군번 중복 체크보다 먼저** 하는 이유는, 어차피 잘못된 요청이면 굳이 DB를 조회할 필요가 없기 때문입니다. |
| `Convert.FromBase64String(req.PhotoBase64)` | 안드로이드가 Base64 문자열로 인코딩해서 보낸 사진을 다시 원본 바이트 배열로 되돌립니다. `RecordsController`가 측정 기록 사진을 저장할 때 쓰는 것과 동일한 패턴입니다. |
| `catch (FormatException)` | Base64 형식이 깨져 있으면(전송 중 손상 등) 400을 응답합니다. |
| `PhotoData = photo` | 사진이 없으면(`req.PhotoBase64 == null`) `photo`도 `null`이라, DB에는 그냥 `NULL`로 저장됩니다 — 사진은 여전히 선택 항목입니다. |
| `Convert.ToBase64String(u.PhotoData)` | 목록 조회 시 저장된 바이너리를 다시 Base64 문자열로 바꿔 JSON으로 내려줍니다. 안드로이드 목록 화면이 이 값을 디코딩해서 아이콘에 표시합니다. |

> 백엔드 코드를 수정했다면 서버를 재시작(`dotnet run`)해야 반영됩니다.

### 이 코드가 하는 일 (초보자를 위한 설명)

- `ScrollView`로 전체를 감싼 이유: 입력 필드가 5개나 되고, 키보드가 화면 아래쪽을 가리기
  때문에 화면이 작은 기기에서도 아래쪽 필드까지 스크롤해서 접근할 수 있게 하기 위해서입니다.
- `TextInputLayout` + `TextInputEditText` 조합은 이 프로젝트의 다른 입력 화면
  (`activity_login.xml`, `fragment_record_input.xml`)에서도 쓰인 표준 패턴입니다.
  `hint` 속성이 입력 필드 위에 떠 있는 라벨(플로팅 라벨)로 표시됩니다.
- `android:id="@+id/etXxx"` — 각 입력창에 붙인 이름표입니다. 나중에 Kotlin 코드에서
  `dialogBinding.etMilitaryId` 처럼 이 id로 접근해서 사용자가 입력한 값을 읽어옵니다.
- 비밀번호 입력 필드만 `android:inputType="textPassword"`를 사용해 입력값이
  점(•)으로 가려지게 했습니다.
- 계급/소속 부대는 자유 입력(EditText) 대신 **Spinner(드롭다운)**로 만들었습니다.
  서버가 인정하는 계급 목록(`GET /api/members/ranks`)과 소속 부대 목록
  (`GET /api/members/units`)을 각각 [MemberListViewModel]이 미리 불러와 두고,
  다이얼로그를 열 때 그 목록으로 스피너를 채웁니다 — 관리자가 자유롭게 글자를
  입력하다가 서버가 모르는 계급이나 존재하지 않는 부대 id를 실수로 보내는 일을
  원천 차단하기 위해서입니다. `@drawable/spinner_background`는 이 프로젝트의
  다른 스피너(`fragment_record_input.xml` 등)와 모양을 통일하기 위한 배경입니다.
  계급/소속 부대는 **필수 항목**이라 "선택 안함" 옵션 없이 항상 실제 값 중
  하나가 선택돼 있습니다 (라벨의 `*`가 필수임을 표시).
- 얼굴 사진은 `ImageView`(미리보기) + 버튼 2개(촬영/갤러리)로 구성했습니다.
  `ivMemberPhotoPreview`는 사진을 고르기 전에는 빈 배경색(`#E8EAF6`)만 보이다가,
  촬영/선택이 끝나면 그 이미지로 채워집니다. 얼굴 사진은 **선택 항목**이라
  아무것도 고르지 않아도 등록에는 문제가 없습니다.

XML 파일을 저장하면, Android의 **ViewBinding** 기능이 자동으로
`DialogAddMemberBinding`이라는 Kotlin 클래스를 생성해줍니다. (이 프로젝트는
`app/build.gradle.kts`에 `viewBinding = true`가 설정되어 있어서 별도 설정 없이 바로 사용 가능합니다.)

> ⚠️ 파일을 새로 만들거나 수정한 직후에는 `DialogAddMemberBinding` 클래스가
> 아직 생성되지 않아 안드로이드 스튜디오에서 빨간 줄(에러)로 보일 수 있습니다.
> 이럴 때는 `Build > Make Project`(또는 아래 4단계의 빌드 명령)를 한 번 실행하면
> 바인딩 클래스가 만들어지면서 에러가 사라집니다.

## 4. Step 2 — ViewModel에 상태/통신 로직 추가하고 Fragment에 연결하기

MVVM 구조에서는 "서버 호출 + 결과 상태 보관"과 "화면에 그리기"를 분리합니다.
그래서 이 단계는 두 파일을 함께 수정합니다.

- `ui/member/MemberListViewModel.kt` — 대원 목록/계급/부대 목록을 서버에서 불러오고,
  신규 대원 등록을 요청하는 로직 (새 파일이면 새로 만들고, 이미 있다면 메서드만 추가)
- `ui/member/MemberListFragment.kt` — 위 ViewModel을 관찰(observe)해서 화면에 반영하고,
  버튼 클릭 시 다이얼로그를 띄우는 로직

### 4-1. `MemberListViewModel`에 상태와 서버 통신 로직 추가

**파일 위치**: `app/src/main/java/com/training/monitor/ui/member/MemberListViewModel.kt`

```kotlin
class MemberListViewModel(application: Application) : AndroidViewModel(application) {

    // 대원 목록. Fragment에는 읽기 전용 LiveData만 노출하고, 값 변경은 이 클래스 내부에서만 한다.
    private val _members = MutableLiveData<List<MemberDto>>(emptyList())
    val members: LiveData<List<MemberDto>> = _members

    // ViewModel은 Context/View를 몰라야 하므로 Toast를 직접 띄울 수 없다 — 대신 "보여줄
    // 메시지"만 LiveData로 흘려보내고, 실제로 Toast를 띄우는 일은 이를 관찰하는 Fragment가 맡는다.
    private val _toastMessage = MutableLiveData<String?>(null)
    val toastMessage: LiveData<String?> = _toastMessage

    // 서버가 인정하는 계급 목록(GET /api/members/ranks) — "대원 추가" 다이얼로그의 계급
    // 스피너가 이 목록으로 채워진다. 자유 입력을 막아 서버가 모르는 값이 저장되는 걸 차단한다.
    private val _ranks = MutableLiveData<List<String>>(emptyList())
    val ranks: LiveData<List<String>> = _ranks

    // 서버가 인정하는 소속 부대 목록(GET /api/members/units) — "대원 추가" 다이얼로그의
    // 소속 부대 스피너가 이 목록으로 채워진다.
    private val _units = MutableLiveData<List<UnitDto>>(emptyList())
    val units: LiveData<List<UnitDto>> = _units

    /** 서버에서 대원 목록을 불러와 [members]를 갱신한다. */
    fun loadMembers() {
        val api = RetrofitClient.create(getApplication())
        // Fragment의 생명주기에 묶인 lifecycleScope 대신 ViewModel의 생명주기에 묶인
        // viewModelScope를 사용한다. 화면 회전 등으로 Fragment의 View가 재생성되어도
        // ViewModel은 살아있으므로, 이미 시작된 네트워크 요청이 중간에 끊기지 않는다.
        viewModelScope.launch {
            try {
                val response = api.getMembers()
                if (response.isSuccessful) {
                    _members.value = response.body() ?: emptyList()
                }
            } catch (e: Exception) {
                _toastMessage.value = "대원 목록 로딩 실패"
            }
        }
    }

    /** 서버에서 등록 가능한 계급 목록을 불러와 [ranks]를 갱신한다. */
    fun loadRanks() {
        val api = RetrofitClient.create(getApplication())
        viewModelScope.launch {
            try {
                val response = api.getRanks()
                if (response.isSuccessful) {
                    _ranks.value = response.body() ?: emptyList()
                }
            } catch (e: Exception) {
                _toastMessage.value = "계급 목록 로딩 실패"
            }
        }
    }

    /** 서버에서 등록 가능한 소속 부대 목록을 불러와 [units]를 갱신한다. */
    fun loadUnits() {
        val api = RetrofitClient.create(getApplication())
        viewModelScope.launch {
            try {
                val response = api.getUnits()
                if (response.isSuccessful) {
                    _units.value = response.body() ?: emptyList()
                }
            } catch (e: Exception) {
                _toastMessage.value = "소속 부대 목록 로딩 실패"
            }
        }
    }

    /**
     * 서버에 신규 대원 등록을 요청하고, 성공 시 목록을 새로고침한다.
     * [photoUri]가 있으면 축소/압축/Base64 인코딩한 뒤 요청에 실어 보낸다. 인코딩은 파일 디코드·압축이
     * 포함된 무거운 작업이라 [Dispatchers.IO]에서 실행해 메인 스레드가 멈추지 않게 한다.
     */
    fun createMember(req: CreateMemberRequest, photoUri: Uri? = null) {
        val api = RetrofitClient.create(getApplication())
        viewModelScope.launch {
            try {
                val photoBase64 = photoUri?.let { withContext(Dispatchers.IO) { encodePhotoBase64(it) } }
                val response = api.createMember(req.copy(photoBase64 = photoBase64))
                if (response.isSuccessful) {
                    _toastMessage.value = "${req.name} 대원을 등록했습니다."
                    loadMembers()
                } else if (response.code() == 409) {
                    _toastMessage.value = "이미 등록된 군번입니다."
                } else {
                    _toastMessage.value = "대원 등록 실패"
                }
            } catch (e: Exception) {
                _toastMessage.value = "서버 연결 실패: ${e.message}"
            }
        }
    }

    /**
     * 카메라 촬영(파일 Uri) 또는 갤러리 선택(콘텐츠 Uri) 결과를 긴 변 480px 이하로 축소하고
     * JPEG 품질 75로 압축해 Base64로 인코딩한다.
     */
    private fun encodePhotoBase64(uri: Uri): String? {
        val resolver = getApplication<Application>().contentResolver

        // inJustDecodeBounds=true 모드에서는 decodeStream이 항상 null을 반환하므로(치수만 bounds에 채움),
        // 반환값이 아니라 bounds.outWidth/outHeight로 디코딩 성공 여부를 판단한다.
        val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
        resolver.openInputStream(uri)?.use { BitmapFactory.decodeStream(it, null, bounds) }
        if (bounds.outWidth <= 0 || bounds.outHeight <= 0) return null

        var sampleSize = 1
        while (bounds.outWidth / sampleSize > 480 || bounds.outHeight / sampleSize > 480) {
            sampleSize *= 2
        }

        val bitmap = resolver.openInputStream(uri)?.use {
            BitmapFactory.decodeStream(it, null, BitmapFactory.Options().apply { inSampleSize = sampleSize })
        } ?: return null

        val output = ByteArrayOutputStream()
        bitmap.compress(Bitmap.CompressFormat.JPEG, 75, output)
        return Base64.encodeToString(output.toByteArray(), Base64.NO_WRAP)
    }

    /** Fragment가 메시지를 Toast로 보여준 뒤 호출한다 — 값을 비워야 화면 회전 시 같은 메시지가 다시 뜨지 않는다. */
    fun onToastMessageShown() {
        _toastMessage.value = null
    }
}
```

> `AndroidViewModel`을 상속하는 이유는 `RetrofitClient.create()`가 `Context`를
> 필요로 하기 때문입니다. 일반 `ViewModel`은 Context를 가질 수 없어서, Application
> Context를 제공하는 `AndroidViewModel`(그리고 `getApplication()`)을 대신 사용합니다.
> `encodePhotoBase64()`도 같은 이유로 `getApplication<Application>().contentResolver`를
> 사용합니다.

> ⚠️ **자주 하는 실수**: `BitmapFactory.decodeStream(...)`을 `inJustDecodeBounds = true`
> 옵션으로 호출하면(이미지 크기만 알아내고 실제 디코딩은 하지 않는 모드) **항상 `null`을
> 반환합니다.** 이 반환값을 `?: return null`처럼 "성공/실패 판정"에 써버리면, 파일이
> 멀쩡해도 매번 조기 종료되어 사진이 계속 `null`로 전송되는 버그가 생깁니다. 대신
> `bounds.outWidth`/`bounds.outHeight`가 채워졌는지로 성공 여부를 판단해야 합니다
> (위 코드의 `if (bounds.outWidth <= 0 || bounds.outHeight <= 0) return null`).

`encodePhotoBase64()`를 쓰려면 파일 상단에 아래 import가 추가로 필요합니다.

```kotlin

import android.net.Uri
import android.util.Base64

import kotlinx.coroutines.withContext
import java.io.ByteArrayOutputStream
```

### 4-2. Fragment에서 ViewModel 연결하기

**파일 위치**: `app/src/main/java/com/training/monitor/ui/member/MemberListFragment.kt`

먼저 파일 맨 위 `import` 목록에 아래 항목들을 추가합니다.


클래스 안(필드 선언부)에 ViewModel 인스턴스와 사진 촬영/선택 관련 상태를 추가합니다.

```kotlin
// by viewModels()는 이 Fragment의 생명주기에 맞는 ViewModel 인스턴스를 만들어(또는 재사용해)준다.
private val viewModel: MemberListViewModel by viewModels()

// "대원 추가" 다이얼로그가 떠 있는 동안에만 유효한 사진 미리보기 참조. 카메라/갤러리 액티비티가
// 떠 있는 동안에도 다이얼로그 자체는 살아있으므로, 결과 콜백에서 이 참조로 미리보기를 갱신한다.
// 다이얼로그가 닫히면 null로 해제해 잘못된 화면을 건드리지 않게 한다.
private var addMemberDialogBinding: DialogAddMemberBinding? = null

// 촬영/선택된 얼굴 사진의 최종 Uri. 다이얼로그의 "등록" 버튼을 누를 때 이 값을 ViewModel에 넘긴다.
private var selectedMemberPhotoUri: Uri? = null

// launchMemberCamera()가 만들어둔 "촬영 시도 중" 파일/uri. 카메라가 성공을 돌려줘야 selectedMemberPhotoUri로 승격된다.
private var candidateMemberPhotoFile: File? = null
private var candidateMemberPhotoUri: Uri? = null

private val memberCameraLauncher = registerForActivityResult(ActivityResultContracts.TakePicture()) { success ->
    if (success) {
        selectedMemberPhotoUri = candidateMemberPhotoUri
        addMemberDialogBinding?.ivMemberPhotoPreview?.setImageURI(selectedMemberPhotoUri)
    } else {
        candidateMemberPhotoFile?.delete()
    }
    candidateMemberPhotoFile = null
    candidateMemberPhotoUri = null
}

private val memberGalleryLauncher = registerForActivityResult(ActivityResultContracts.GetContent()) { uri ->
    if (uri != null) {
        selectedMemberPhotoUri = uri
        addMemberDialogBinding?.ivMemberPhotoPreview?.setImageURI(uri)
    }
}
```

> `registerForActivityResult(...)`는 반드시 Fragment가 `CREATED` 상태가 되기 전
> (즉 클래스의 필드 선언부)에 등록해야 합니다. 버튼 클릭 시점(`onViewCreated()` 안)에
> 등록하려고 하면 예외가 발생합니다.

`onViewCreated()` 함수 안, `binding.rvMembers.adapter = adapter` 다음 줄에
버튼 클릭 리스너와 observe 등록, 초기 로딩 호출을 추가합니다.

```kotlin
binding.fabAddMember.setOnClickListener { showAddMemberDialog() }

// 대원 목록이 바뀔 때마다(최초 로딩이든, 등록 성공 후 재조회든) 어댑터/카운트 텍스트를 갱신한다.
viewModel.members.observe(viewLifecycleOwner) { members ->
    adapter.submitList(members)
    binding.tvMemberCount.text = "총 ${members.size}명"
}

// ViewModel이 "보여줄 메시지"를 흘려보내면 Toast로 띄운 뒤 onToastMessageShown()으로 비운다
// (비우지 않으면 화면 회전 시 같은 메시지가 다시 뜬다). 이 observe 하나가 대원 추가/비밀번호
// 재설정 등 이 화면의 모든 성공·실패 메시지를 공통으로 처리한다.
viewModel.toastMessage.observe(viewLifecycleOwner) { message ->
    if (message != null) {
        Toast.makeText(requireContext(), message, Toast.LENGTH_SHORT).show()
        viewModel.onToastMessageShown()
    }
}

viewModel.loadMembers()
viewModel.loadRanks()
viewModel.loadUnits()
```

이 한 줄 `binding.fabAddMember.setOnClickListener { showAddMemberDialog() }`이
바로 "버튼과 동작을 연결"하는 핵심 코드입니다. 버튼(`fabAddMember`)을 클릭하면
`showAddMemberDialog()`라는 함수를 실행하라는 뜻입니다. (이 함수는 다음 단계에서
직접 만듭니다.)

### 4-3. 다이얼로그를 띄우는 함수 추가

클래스 안 아무 곳(다른 `private fun` 옆)에 아래 함수를 추가합니다. 실제 서버
호출은 이제 이 함수가 아니라 4-1에서 만든 `viewModel.createMember()`가 담당합니다.

```kotlin
/** 군번/이름/초기 비밀번호/계급/소속 부대(필수)와 얼굴 사진(선택)을 입력받아 신규 대원을 등록하는 다이얼로그를 띄운다. */
private fun showAddMemberDialog() {
    val dialogBinding = DialogAddMemberBinding.inflate(layoutInflater)
    addMemberDialogBinding = dialogBinding
    selectedMemberPhotoUri = null

    // 계급 스피너 — 자유 입력 대신 서버가 인정하는 계급 목록(viewModel.ranks)에서만 고르게 한다.
    // 계급은 필수 항목이라 "선택 안함" 옵션 없이 항상 실제 계급 중 하나가 선택돼 있다.
    val ranks = viewModel.ranks.value ?: emptyList()
    dialogBinding.spinnerRank.adapter = ArrayAdapter(
        requireContext(), android.R.layout.simple_spinner_item, ranks
    ).also { it.setDropDownViewResource(android.R.layout.simple_spinner_dropdown_item) }

    // 소속 부대 스피너 — 부대 ID 직접 입력 대신 서버가 인정하는 부대 목록(viewModel.units)에서만 고르게 한다.
    // 소속 부대도 필수 항목이라 "선택 안함" 옵션 없이 항상 실제 부대 중 하나가 선택돼 있다.
    val units = viewModel.units.value ?: emptyList()
    dialogBinding.spinnerUnit.adapter = ArrayAdapter(
        requireContext(), android.R.layout.simple_spinner_item, units.map { it.name }
    ).also { it.setDropDownViewResource(android.R.layout.simple_spinner_dropdown_item) }

    dialogBinding.btnMemberCamera.setOnClickListener { launchMemberCamera() }
    dialogBinding.btnMemberGallery.setOnClickListener { memberGalleryLauncher.launch("image/*") }

    AlertDialog.Builder(requireContext())
        .setTitle("대원 추가")
        .setView(dialogBinding.root)
        .setPositiveButton("등록") { _, _ ->
            val militaryId = dialogBinding.etMilitaryId.text.toString().trim()
            val name = dialogBinding.etName.text.toString().trim()
            val password = dialogBinding.etPassword.text.toString()
            val rank = ranks.getOrNull(dialogBinding.spinnerRank.selectedItemPosition)
            val unitId = units.getOrNull(dialogBinding.spinnerUnit.selectedItemPosition)?.id

            if (militaryId.isEmpty() || name.isEmpty() || password.isEmpty()) {
                Toast.makeText(requireContext(), "군번, 이름, 비밀번호는 필수입니다.", Toast.LENGTH_SHORT).show()
            } else if (rank == null || unitId == null) {
                Toast.makeText(requireContext(), "계급과 소속 부대는 필수입니다.", Toast.LENGTH_SHORT).show()
            } else {
                // 기존에는 Fragment가 직접 API를 호출했지만, 이제는 ViewModel에 요청만
                // 위임한다. 결과(성공/실패 메시지, 목록 갱신)는 4-2에서 등록한 observe
                // 콜백들이 알아서 처리한다.
                viewModel.createMember(
                    CreateMemberRequest(militaryId, name, password, rank, unitId),
                    selectedMemberPhotoUri
                )
            }
        }
        .setNegativeButton("취소", null)
        .setOnDismissListener { addMemberDialogBinding = null }
        .show()
}

/** 앱 캐시 폴더에 임시 파일을 만들고, FileProvider로 카메라 앱에 대원 얼굴 사진 촬영을 요청한다. */
private fun launchMemberCamera() {
    val imagesDir = File(requireContext().cacheDir, "images").apply { mkdirs() }
    val file = File.createTempFile("member_", ".jpg", imagesDir)
    val uri = FileProvider.getUriForFile(requireContext(), "${requireContext().packageName}.fileprovider", file)
    candidateMemberPhotoFile = file
    candidateMemberPhotoUri = uri
    memberCameraLauncher.launch(uri)
}
```

### 이 코드가 하는 일 (한 줄씩 설명)

**`MemberListViewModel`**

| 코드 | 설명 |
|---|---|
| `_members` / `members` | 뒤에 `_`가 붙은 쪽은 이 클래스 내부에서만 값을 바꿀 수 있는 `MutableLiveData`이고, 밖으로는 읽기 전용 `LiveData`만 노출합니다. Fragment가 실수로 목록을 직접 덮어쓰는 걸 막기 위한 관례입니다. |
| `viewModelScope.launch { ... }` | 네트워크 요청은 시간이 걸리므로, 코루틴(비동기 작업)으로 실행합니다. Fragment의 `lifecycleScope`와 달리 화면 회전으로 View가 재생성돼도 취소되지 않습니다. |
| `api.getMembers()` / `api.createMember(req)` | 실제로 서버에 `GET /api/members`, `POST /api/members` 요청을 보냅니다. |
| `response.isSuccessful` | 서버가 200번대 성공 응답을 주면 참(true)입니다. |
| `response.code() == 409` | 서버가 "이미 등록된 군번"일 때 409 Conflict를 내려주도록 만들어져 있습니다. 이 경우를 따로 구분해서 더 친절한 메시지를 보여줍니다. |
| `catch (e: Exception)` | 서버 자체에 연결이 안 되는 경우(서버가 꺼져있거나 네트워크 문제)를 처리합니다. |

| `photoUri?.let { encodePhotoBase64(it) }` | 사진을 안 골랐으면(`photoUri == null`) 그대로 `null`, 골랐으면 리사이즈/압축/Base64 인코딩한 문자열을 얻습니다. |

```kotlin
    binding.ivProfilePhoto.setImageBitmap(bitmap)
    binding.ivProfilePhoto.visibility = View.VISIBLE
    binding.tvProfileEmoji.visibility = View.GONE
} else {
    binding.ivProfilePhoto.visibility = View.GONE
```

# 파트 B. 비밀번호 재설정 기능

## 8. 무엇을 만드는가

대원이 비밀번호를 잊어버렸을 때, 이 앱에는 "이메일로 재설정 링크 받기" 같은
자가 처리 기능이 없습니다. 서버의 `User` 데이터에는 애초에 이메일/전화번호
필드 자체가 없기 때문입니다 (군번, 이름, 계급, 역할, 소속 부대만 있음).

대신 **관리자가 대원 목록에서 대원을 클릭하면, 새 비밀번호를 입력받아
서버에 반영해주는 방식**으로 구현합니다. 이 앱이 이미 사용 중인
"관리자가 대신 처리한다"는 패턴(`createMember`, `deactivateMember`)과
동일한 접근입니다.

파트 A와 다른 점: **이번에는 서버(백엔드)에도 새 API를 하나 추가해야 합니다.**
서버 쪽에 비밀번호를 재설정하는 엔드포인트가 아직 없기 때문입니다.

우리가 할 일은 3가지입니다.

1. 백엔드(`TrainingMonitor`, ASP.NET Core)에 비밀번호 재설정 API 추가하기
2. 안드로이드에서 그 API를 호출하기 위한 DTO/인터페이스 추가하기
3. 파트 A에서 만든 `MemberListViewModel`에 재설정 요청 메서드를 추가하고,

## 9. Step 1 — 백엔드에 비밀번호 재설정 API 추가하기

**파일 위치**: `TrainingMonitor/Controllers/MembersController.cs`
(`AdTrainingMonitor`가 아니라 **별도의 백엔드 프로젝트**입니다.)

기존의 `CreateMember`, `DeactivateMember` 메서드 옆에 아래 메서드를 추가합니다.

```csharp
// 대원 비밀번호 재설정 (관리자가 대신 새 비밀번호로 교체)
[HttpPatch("{id}/password")]
public async Task<IActionResult> ResetPassword(long id, [FromBody] ResetPasswordRequest req)
{
    var user = await db.Users.FindAsync(id);
    if (user is null) return NotFound();

    user.PasswordHash = BCrypt.Net.BCrypt.HashPassword(req.NewPassword);
    user.UpdatedAt = DateTime.UtcNow;
    await db.SaveChangesAsync();
    return NoContent();
}
```

그리고 파일 맨 아래, 기존 `CreateMemberRequest` record 옆에 요청 바디 모양을
정의하는 record를 하나 추가합니다.

```csharp
public record ResetPasswordRequest(string NewPassword);
```

### 이 코드가 하는 일

| 코드 | 설명 |
|---|---|
| `[HttpPatch("{id}/password")]` | `PATCH /api/members/{id}/password` 요청을 받는 엔드포인트임을 선언합니다. 클래스 전체에 걸려있는 `[Authorize(Roles = "ADMIN")]` 덕분에 이 메서드도 자동으로 관리자만 호출할 수 있습니다 — 이미 있던 `createMember`, `deactivateMember`와 동일하게 별도의 권한 체크 코드가 필요 없습니다. |
| `db.Users.FindAsync(id)` | URL의 `{id}`로 전달된 대원을 DB에서 찾습니다. |
| `user is null → NotFound()` | 존재하지 않는 대원 id면 404를 응답합니다. |
| `BCrypt.Net.BCrypt.HashPassword(req.NewPassword)` | 비밀번호를 평문 그대로 저장하지 않고, `CreateMember`에서 쓰던 것과 똑같은 방식으로 해시(암호화)해서 저장합니다. |
| `return NoContent();` | 성공하면 별도의 응답 데이터 없이 204 No Content를 돌려줍니다. |

`ResetPasswordRequest(string NewPassword)` record는 JSON으로 받을 요청 바디의
모양을 정의합니다. 이 프로젝트는 `Program.cs`에 `SnakeCaseNamingPolicy`가
전역 설정되어 있어서, C#의 `NewPassword`는 요청 JSON에서는 자동으로
`new_password`로 매핑됩니다 — 별도 설정을 추가하지 않아도 됩니다.

> 백엔드 코드를 수정했다면 서버를 재시작(`dotnet run`)해야 새 엔드포인트가
> 반영됩니다. 이미 서버가 실행 중이라면 먼저 프로세스를 종료한 뒤 다시
> 실행하세요.

## 10. Step 2 — 안드로이드에 요청 DTO와 API 메서드 추가하기

### 10-1. 요청 데이터 모양 — `Dtos.kt`

**파일 위치**: `app/src/main/java/com/training/monitor/data/model/Dtos.kt`

기존 `CreateMemberRequest` 옆에 아래 데이터 클래스를 추가합니다.

```kotlin
/** 대원 비밀번호 재설정(PATCH /api/members/{id}/password) 요청 바디. CreateMemberRequest와 마찬가지로 관리자 권한이 필요하다. */
data class ResetPasswordRequest(

```

`@SerializedName("new_password")`는 Kotlin의 `newPassword`(카멜케이스) 프로퍼티를
JSON으로 변환할 때 `new_password`(스네이크케이스)로 바꿔주는 어노테이션입니다.
Step 1에서 본 서버의 `SnakeCaseNamingPolicy`와 짝이 맞아야 하므로 반드시 필요합니다.

### 10-2. API 인터페이스 — `ApiService.kt`

**파일 위치**: `app/src/main/java/com/training/monitor/data/api/ApiService.kt`

```kotlin
/** 대원의 비밀번호를 관리자가 새 값으로 재설정한다. */
```

`@Path("id")`는 URL의 `{id}` 자리에 실제 대원 id를 채워 넣으라는 뜻이고,

### 11-1. `MemberListViewModel`에 재설정 메서드 추가

**파일 위치**: `app/src/main/java/com/training/monitor/ui/member/MemberListViewModel.kt`

파트 A에서 만든 클래스 안, 다른 `fun` 옆에 아래 메서드를 추가합니다.

```kotlin
/** 서버에 비밀번호 재설정을 요청한다. */
fun resetPassword(member: MemberDto, newPassword: String) {
    val api = RetrofitClient.create(getApplication())
    viewModelScope.launch {
        try {
            val response = api.resetPassword(member.id, ResetPasswordRequest(newPassword))
            _toastMessage.value = if (response.isSuccessful) {
                "${member.name}의 비밀번호를 재설정했습니다."
            } else {
                "비밀번호 재설정 실패"
            }
        } catch (e: Exception) {
            _toastMessage.value = "서버 연결 실패: ${e.message}"
        }
    }
}
```

### 11-2. Fragment에서 대원 항목 클릭 시 다이얼로그 띄우기

**파일 위치**: `app/src/main/java/com/training/monitor/ui/member/MemberListFragment.kt`

파일 상단 import 목록에 아래 2줄을 추가합니다. (`ResetPasswordRequest`는

```kotlin
import android.text.InputType
import android.widget.EditText
```

`onViewCreated()` 함수 안, 파트 A의 `binding.fabAddMember.setOnClickListener { ... }`
옆에 아래 한 줄을 추가합니다.

```kotlin

```

`MemberAdapter.kt`에는 이미 `onItemClick`이라는 콜백 변수가 정의되어 있었지만
(`var onItemClick: ((MemberDto) -> Unit)? = null`), 지금까지 아무도 연결해주지
않아서 대원 항목을 눌러도 반응이 없었습니다. 이 한 줄로 "항목 클릭 → 비밀번호

클래스 안에 다이얼로그를 띄우는 함수를 추가합니다. (실제 서버 호출은 11-1에서
만든 `viewModel.resetPassword()`가 담당합니다.)

```kotlin
/** 대원 항목 클릭 시 새 비밀번호를 입력받아 서버에 재설정을 요청하는 다이얼로그를 띄운다. */
private fun showResetPasswordDialog(member: MemberDto) {
    val input = EditText(requireContext()).apply {
        inputType = InputType.TYPE_CLASS_TEXT or InputType.TYPE_TEXT_VARIATION_PASSWORD
        hint = "새 비밀번호"
    }

    AlertDialog.Builder(requireContext())
        .setTitle("${member.name} 비밀번호 재설정")
        .setView(input)
        .setPositiveButton("확인") { _, _ ->
            val newPassword = input.text.toString()
            if (newPassword.isEmpty()) {
                Toast.makeText(requireContext(), "새 비밀번호를 입력하세요.", Toast.LENGTH_SHORT).show()
            } else {
                viewModel.resetPassword(member, newPassword)
            }
        }
        .setNegativeButton("취소", null)
        .show()
}
```

### 이 코드가 하는 일

**`MemberListViewModel.resetPassword()`**

| 코드 | 설명 |
|---|---|
| `api.resetPassword(member.id, ResetPasswordRequest(newPassword))` | Step 2에서 만든 API를 호출합니다. `member.id`는 대원 목록을 조회할 때 서버가 내려준 DB의 실제 id 값입니다. |
| `response.isSuccessful` | 서버가 204 No Content를 돌려주면 성공으로 처리합니다 (별도로 돌려받을 데이터가 없으므로 `response.body()`를 확인할 필요가 없습니다). |
| `_toastMessage.value = ...` | 성공/실패 메시지를 LiveData에 담아두기만 합니다. 실제 Toast 표시는 파트 A에서 등록해 둔 Fragment의 `viewModel.toastMessage.observe { ... }`가 처리합니다. |

**`MemberListFragment.showResetPasswordDialog()`**

| 코드 | 설명 |
|---|---|
| `EditText(requireContext()).apply { ... }` | 파트 A처럼 별도 XML 레이아웃을 만들지 않고, 입력창이 1개뿐이라 코드로 직접 `EditText` 하나를 만들었습니다. 입력 필드가 여러 개면 파트 A처럼 XML+ViewBinding 방식이 낫고, 1개뿐이면 이렇게 코드로 즉석에서 만드는 것도 흔한 방법입니다. |
| `TYPE_CLASS_TEXT or TYPE_TEXT_VARIATION_PASSWORD` | 입력값을 점(•)으로 가려지는 비밀번호 입력창으로 만듭니다. |
| `.setTitle("${member.name} 비밀번호 재설정")` | 다이얼로그 제목에 클릭한 대원의 이름을 넣어, "누구의 비밀번호를 바꾸는지" 명확히 보여줍니다. |
| `viewModel.resetPassword(member, newPassword)` | 실제 재설정 요청은 ViewModel에 위임합니다. Fragment는 결과를 기다리지 않고, 결과가 오면 파트 A에서 등록해 둔 `toastMessage` observe가 자동으로 Toast를 띄웁니다. |

# 파트 C. 대원 정보 수정 기능

## 15. 무엇을 만드는가

파트 A에서 대원을 "등록"만 할 수 있었는데, 등록 후에 이름을 잘못 입력했거나 계급이
바뀌었거나 얼굴 사진을 다시 찍고 싶을 때 고칠 방법이 없었습니다. 이 파트에서는
대원 목록의 각 행에 **연필 아이콘**을 추가하고, 누르면 이름/계급/소속 부대/얼굴
사진을 수정할 수 있는 다이얼로그를 띄웁니다.

**군번과 비밀번호는 이 기능으로 바꾸지 않습니다** — 군번은 로그인 식별자라 바뀌면
안 되고, 비밀번호는 이미 파트 B의 "비밀번호 재설정" 기능이 따로 담당합니다.

파트 B와 마찬가지로 서버에 아직 "수정" API가 없으므로, 이번에도 **백엔드 +
안드로이드를 함께 수정**합니다. 얼굴 사진은 세 가지 상태를 구분해야 해서 조금
까다롭습니다.

- **사진을 안 건드림** → 기존 사진 그대로 유지
- **새 사진을 촬영/선택함** → 기존 사진을 새 사진으로 교체
- **"사진 삭제" 버튼을 누름** → 사진을 완전히 지움(무사진 상태로)

## 16. Step 0 — 백엔드: 대원 정보 수정 API 추가하기

**파일 위치**: `TrainingMonitor/Controllers/MembersController.cs`

기존 `CreateMember` 메서드 옆에 추가합니다.

```csharp
[HttpPatch("{id}")]
public async Task<IActionResult> UpdateMember(long id, [FromBody] UpdateMemberRequest req)
{
    if (string.IsNullOrWhiteSpace(req.Name) || string.IsNullOrWhiteSpace(req.Rank) || req.UnitId is null)
        return BadRequest("이름, 계급, 소속 부대는 필수입니다.");

    var user = await db.Users.FindAsync(id);
    if (user is null) return NotFound();

    // 사진 변경은 세 가지 경우로 나뉜다: 삭제 요청 / 새 사진 첨부 / 아무 지시 없음(기존 사진 유지).
    if (req.RemovePhoto)
    {
        user.PhotoData = null;
    }
    else if (req.PhotoBase64 is not null)
    {
        try
        {
            user.PhotoData = Convert.FromBase64String(req.PhotoBase64);
        }
        catch (FormatException)
        {
            return BadRequest("잘못된 사진 데이터입니다.");
        }
    }

    user.Name = req.Name;
    user.Rank = req.Rank;
    user.UnitId = req.UnitId;
    user.UpdatedAt = DateTime.UtcNow;
    await db.SaveChangesAsync();
    return NoContent();
}
```

요청 바디 모양을 정의하는 record도 추가합니다.

```csharp
public record UpdateMemberRequest(
    string Name,
    string? Rank,
    long? UnitId,
    string? PhotoBase64,
    bool RemovePhoto
);
```

### 이 코드가 하는 일

| 코드 | 설명 |
|---|---|
| `[HttpPatch("{id}")]` | `PATCH /api/members/{id}/password`(파트 B)와 경로가 겹치지 않는 `PATCH /api/members/{id}`를 새로 선언합니다. 두 라우트는 뒤에 `/password`가 붙는지 여부로 구분됩니다. |
| 필수값 검사가 사진 검사보다 먼저 | 이름/계급/부대 중 하나라도 없으면 사진 데이터를 굳이 디코딩하기 전에 바로 400을 반환합니다. |
| `if (req.RemovePhoto) ... else if (req.PhotoBase64 is not null) ...` | **삭제가 항상 교체보다 우선**입니다. 안드로이드 쪽에서 이 둘을 동시에 true/non-null로 보내지 않도록 관리하지만, 서버도 방어적으로 삭제를 먼저 체크합니다. 둘 다 해당 안 되면(`else` 없음) `user.PhotoData`를 그대로 둬서 기존 사진이 유지됩니다. |
| `user.UpdatedAt = DateTime.UtcNow` | 다른 수정 API(`DeactivateMember`, `ResetPassword`)와 동일하게 수정 시각을 갱신합니다. |

그리고 클래스 안에 다이얼로그 함수를 추가합니다.

```kotlin
/**
 * 연필 아이콘 클릭 시 이름/계급/소속 부대/얼굴 사진을 수정하는 다이얼로그를 띄운다.
 * 군번/비밀번호는 이 다이얼로그로 바꿀 수 없다 (군번은 로그인 식별자, 비밀번호는 별도 기능).
 */
private fun showEditMemberDialog(member: MemberDto) {
    val dialogBinding = DialogEditMemberBinding.inflate(layoutInflater)
    editMemberDialogBinding = dialogBinding
    addMemberDialogBinding = null
    selectedMemberPhotoUri = null
    editRemovePhoto = false

    dialogBinding.etEditName.setText(member.name)

    // 계급 스피너 — 현재 계급이 목록에 있으면 그 위치를 기본 선택값으로 맞춰준다.
    val ranks = viewModel.ranks.value ?: emptyList()
    dialogBinding.spinnerEditRank.adapter = ArrayAdapter(
        requireContext(), android.R.layout.simple_spinner_item, ranks
    ).also { it.setDropDownViewResource(android.R.layout.simple_spinner_dropdown_item) }
    ranks.indexOf(member.rank).takeIf { it >= 0 }?.let { dialogBinding.spinnerEditRank.setSelection(it) }

    // 소속 부대 스피너 — MemberDto는 unitId 없이 전체 경로 이름(unitName)만 갖고 있으므로,
    // units 목록에서 같은 이름을 찾아 그 위치를 기본 선택값으로 맞춰준다.
    val units = viewModel.units.value ?: emptyList()
    dialogBinding.spinnerEditUnit.adapter = ArrayAdapter(
        requireContext(), android.R.layout.simple_spinner_item, units.map { it.name }
    ).also { it.setDropDownViewResource(android.R.layout.simple_spinner_dropdown_item) }
    units.indexOfFirst { it.name == member.unitName }.takeIf { it >= 0 }
        ?.let { dialogBinding.spinnerEditUnit.setSelection(it) }

    // 기존 사진이 있으면 미리보기에 미리 띄워 둔다 — 아무것도 안 건드리면 이 사진이 그대로 유지된다.
    if (member.photoBase64 != null) {
        val bytes = Base64.decode(member.photoBase64, Base64.NO_WRAP)
        val bitmap = BitmapFactory.decodeByteArray(bytes, 0, bytes.size)
        dialogBinding.ivEditMemberPhotoPreview.setImageBitmap(bitmap)
    }

    dialogBinding.btnEditMemberCamera.setOnClickListener { launchMemberCamera() }
    dialogBinding.btnEditMemberGallery.setOnClickListener { memberGalleryLauncher.launch("image/*") }
    dialogBinding.btnEditMemberRemovePhoto.setOnClickListener {
        editRemovePhoto = true
        selectedMemberPhotoUri = null
        dialogBinding.ivEditMemberPhotoPreview.setImageDrawable(null)
    }

    AlertDialog.Builder(requireContext())
        .setTitle("${member.name} 정보 수정")
        .setView(dialogBinding.root)
        .setPositiveButton("저장") { _, _ ->
            val name = dialogBinding.etEditName.text.toString().trim()
            val rank = ranks.getOrNull(dialogBinding.spinnerEditRank.selectedItemPosition)
            val unitId = units.getOrNull(dialogBinding.spinnerEditUnit.selectedItemPosition)?.id

            if (name.isEmpty()) {
                Toast.makeText(requireContext(), "이름은 필수입니다.", Toast.LENGTH_SHORT).show()
            } else if (rank == null || unitId == null) {
                Toast.makeText(requireContext(), "계급과 소속 부대는 필수입니다.", Toast.LENGTH_SHORT).show()
            } else {
                viewModel.updateMember(
                    member.id,
                    UpdateMemberRequest(name, rank, unitId),
                    selectedMemberPhotoUri,
                    editRemovePhoto
                )
            }
        }
        .setNegativeButton("취소", null)
        .setOnDismissListener { editMemberDialogBinding = null }
        .show()
}
```

### 17-6. `MemberListViewModel`에 수정 메서드 추가

```kotlin
/**
 * 서버에 기존 대원 정보(이름/계급/소속 부대/얼굴 사진) 수정을 요청하고, 성공 시 목록을 새로고침한다.
 * [photoUri]가 있으면 새 사진으로 교체하고, [removePhoto]가 true면 기존 사진을 지운다
 * (둘 다 지정된 경우 삭제가 우선 적용됨 — [encodePhotoBase64]는 [removePhoto]가 true면 호출하지 않는다).
 */
fun updateMember(memberId: Long, req: UpdateMemberRequest, photoUri: Uri? = null, removePhoto: Boolean = false) {
    val api = RetrofitClient.create(getApplication())
    viewModelScope.launch {
        try {
            val photoBase64 = if (removePhoto) null
                else photoUri?.let { withContext(Dispatchers.IO) { encodePhotoBase64(it) } }
            val response = api.updateMember(memberId, req.copy(photoBase64 = photoBase64, removePhoto = removePhoto))
            if (response.isSuccessful) {
                _toastMessage.value = "${req.name} 정보를 수정했습니다."
                loadMembers()
            } else {
                _toastMessage.value = "대원 정보 수정 실패"
            }
        } catch (e: Exception) {
            _toastMessage.value = "서버 연결 실패: ${e.message}"
        }
    }
}
```

`encodePhotoBase64()`는 파트 A(Step 2)에서 이미 만든 것을 그대로 재사용합니다 — 새로
만들 필요가 없습니다.

### 이 코드가 하는 일

| 코드 | 설명 |
|---|---|
| `ranks.indexOf(member.rank)` | 계급은 문자열 그대로 비교해도 되므로 `indexOf`로 바로 위치를 찾습니다. 못 찾으면(-1) 기본 선택(0번)을 그대로 둡니다. |
| `units.indexOfFirst { it.name == member.unitName }` | `MemberDto`는 부대의 `id`가 아니라 "1여단 1대대"처럼 조립된 전체 경로 이름(`unitName`)만 갖고 있어서, `id`로 바로 찾을 수 없습니다. 대신 `GetUnits()`가 내려주는 `UnitDto.name`도 같은 방식으로 조립되므로, 이름이 같은 항목을 찾아 그 위치를 씁니다. |
| `editRemovePhoto = true; selectedMemberPhotoUri = null` | "사진 삭제"를 누르면 혹시 그 전에 새로 고른 사진이 있었더라도 무효화하고, 미리보기도 비웁니다. |
| `if (removePhoto) null else photoUri?.let { ... }` | ViewModel에서도 "삭제가 우선"을 한 번 더 지킵니다 — `removePhoto`가 true면 새 사진이 있어도 인코딩 자체를 하지 않습니다. |
| `req.copy(photoBase64 = ..., removePhoto = removePhoto)` | Fragment가 넘긴 요청 객체(이름/계급/부대만 채워짐)에 사진 관련 필드만 여기서 마저 채웁니다. |

## 19. 정리 — 세 기능에서 배운 안드로이드/백엔드 개발 패턴

이 세 기능을 완성하면서 사용한 패턴들은 이 프로젝트의 다른 화면에서도 반복적으로
쓰이는 "표준 패턴"입니다. 앞으로 비슷한 기능(예: "측정 세션 추가", "대원 비활성화
확인창" 등)을 만들 때도 그대로 응용할 수 있습니다.

1. **서버 통신·상태는 ViewModel, 화면 그리기는 Fragment** — Fragment는 `RetrofitClient`를
   직접 호출하지 않고, ViewModel의 메서드(`viewModel.createMember(...)`)만 호출합니다.
2. **결과는 LiveData로 노출하고 Fragment가 `observe`하기** — 목록(`members`)처럼 여러 화면
   요소가 같이 갱신돼야 하는 값도, "보여줄 메시지 한 번"(`toastMessage`)처럼 1회성 이벤트도
   전부 LiveData로 흘려보냅니다.
3. **1회성 메시지(Toast)는 값을 다 쓰면 비우기** — `onToastMessageShown()`처럼 소비 후
   `null`로 되돌리는 함수를 하나 두면, 화면 회전으로 Fragment가 재생성돼도 같은 메시지가
   중복으로 뜨지 않습니다.
4. **레이아웃 XML 먼저 그리기** → ViewBinding이 자동으로 Kotlin 클래스를 생성해줌 (입력 필드가 많을 때)
5. **입력 필드가 1개뿐이면 굳이 XML 없이 코드로 `EditText`를 즉석에서 만들어도 됨** (파트 B처럼)
6. **버튼/목록 항목에 `setOnClickListener` (또는 어댑터의 콜백)로 다이얼로그 표시 함수 연결하기**
7. **`AlertDialog.Builder`로 커스텀 입력 폼을 다이얼로그로 띄우고, 값 검증 후 ViewModel에 요청 위임하기**
8. **ViewModel 안에서 `viewModelScope.launch { }`로 `suspend fun` API를 호출하기** (코루틴) —
   Fragment의 `lifecycleScope`와 달리 화면 회전으로 View가 재생성돼도 요청이 끊기지 않습니다.
9. **`response.isSuccessful` / `response.code()`로 성공·실패·특정 에러 코드를 구분해서 처리하기**
10. **성공 시 목록을 다시 불러와(`loadMembers()`) 상태를 최신으로 갱신하기** (파트 A) — 목록
    자체가 안 바뀌는 동작이면 생략 가능 (파트 B)
11. **API가 서버에 아직 없으면, 컨트롤러의 기존 메서드(`CreateMember`, `DeactivateMember`)와 같은 패턴으로 새 엔드포인트를 추가하기** (`[Authorize(Roles = "ADMIN")]`는 클래스에 이미 걸려있으므로 메서드마다 반복할 필요 없음)
12. **사진을 다룰 땐 Base64 인코딩(안드로이드) ↔ `byte[]`/`Convert.FromBase64String`(서버) 왕복 패턴 사용하기** — 이 프로젝트는 `RecordsController`의 기록 사진과 `MembersController`의 얼굴 사진 모두 동일한 방식(파일 크기 제한을 위해 클라이언트에서 리사이즈/압축 후 Base64로 전송 → 서버는 그대로 바이트 배열로 저장)을 씁니다.
13. **`BitmapFactory.decodeStream(..., inJustDecodeBounds = true)`는 항상 `null`을 반환한다** — 이미지 치수만 알아내고 싶을 때 쓰는 이 옵션은 반환값이 아니라 `Options.outWidth`/`outHeight`로 결과를 확인해야 합니다. 반환값을 성공 여부 판단에 쓰면 파일이 멀쩡해도 항상 실패로 처리되는 조용한 버그가 생깁니다.
14. **"수정" 기능의 사진 필드는 세 가지 상태(유지/교체/삭제)를 명시적으로 구분하기** (파트 C) — "등록"은 사진이 있냐 없냐만 따지면 되지만, "수정"은 "아무것도 안 건드림"과 "삭제함"을 반드시 구분해야 합니다. `photoBase64: String?` 하나만으로는 이 둘을 구분할 수 없어서, `removePhoto: Boolean` 플래그를 따로 두고 "삭제가 항상 교체/유지보다 우선"이라는 규칙을 안드로이드·서버 양쪽에 동일하게 적용했습니다.
15. **여러 다이얼로그가 같은 카메라/갤러리 런처를 공유할 땐 "지금 열려 있는 다이얼로그가 어느 쪽인지" 결과 콜백이 알 필요 없게 만들기** (파트 C) — `registerForActivityResult`는 화면(Fragment)당 한 번만 등록할 수 있으므로, "추가"/"수정" 다이얼로그마다 따로 만들지 않고 각 다이얼로그의 바인딩 참조(`addMemberDialogBinding`/`editMemberDialogBinding`)를 콜백에서 모두 갱신하는 방식으로 공유했습니다. 두 참조는 항상 하나만 non-null이므로 안전합니다.

이 패턴들을 이해하면, 이 앱의 다른 "입력 후 저장" 계열 화면
(`RecordInputFragment.kt` + `RecordInputViewModel.kt`의 기록 저장,
`LoginActivity.kt` + `LoginViewModel.kt`의 로그인 등)도 구조적으로 거의 동일하다는
것을 알 수 있습니다.

> 참고로 이 프로젝트는 `RecyclerView.Adapter`(`MemberAdapter`)처럼 자체 상태가 없는
> View 계층 컴포넌트에도 "ui 폴더의 모든 화면 컴포넌트에 대응하는 ViewModel을 둔다"는
> 컨벤션에 맞춰 빈 `MemberAdapterViewModel`을 하나 두고 있습니다. 실제로 값을 담고
> 있진 않으므로, 이 가이드를 따라 만들 때 필수는 아닙니다.

# 부록. 실제 폰에 설치할 릴리스 APK 만들기

지금까지는 `adb install`로 디버그 APK를 PC에 USB로 연결한 폰에만 설치해서 테스트했습니다.
이 부록은 **USB 연결 없이, 다른 사람의 폰에도 파일만 전달해서 설치할 수 있는 릴리스
APK**를 만드는 방법을 정리합니다.

## A-1. 디버그 APK와 릴리스 APK의 차이

| | 디버그 APK | 릴리스 APK |
|---|---|---|
| 서명 | 안드로이드 스튜디오가 자동 생성한 임시 디버그 키 | 우리가 직접 만든 키(키스토어)로 서명 |
| 설치 방법 | 보통 `adb install` (PC 연결 필요) | APK 파일을 폰에 복사해서 직접 설치 가능 |
| 서버 주소(`BASE_URL`) | `http://127.0.0.1:5133/` (USB로 `adb reverse` 포워딩 필요) | PC의 실제 LAN IP (Wi-Fi로 독립 동작) |
| 최적화/난독화 | 없음 | 이 프로젝트는 간단히 끔(`isMinifyEnabled = false`) — 사내 테스트용이라 굳이 켜지 않음 |

같은 앱(`com.training.monitor`)이라도 **서명이 다르면 안드로이드가 "다른 앱"으로 취급**해서,
디버그로 설치된 상태에서 릴리스 APK를 바로 덮어 설치할 수 없습니다(반대도 마찬가지).
기존 앱을 지우고(`adb uninstall com.training.monitor`) 새로 설치해야 합니다 — 서버 쪽
데이터는 그대로 남아있고, 로그인만 다시 하면 됩니다.

## A-2. Step 1 — 서명용 키스토어 만들기

한 번만 만들면 계속 재사용합니다 (매번 새로 만들면 이전 버전과 "다른 앱"이 되어버립니다).

```bash
keytool -genkeypair -v \
  -keystore keyStore/release.keystore \
  -alias trainingmonitor \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -storepass <storepassword> -keypass <keypassword> \
  -dname "CN=TrainingMonitor, OU=Dev, O=TrainingMonitor, L=Seoul, ST=Seoul, C=KR"
```

> **주의**: 최신 `keytool`이 만드는 키스토어 형식(PKCS12)은 저장소 비밀번호와 키 비밀번호를
> **같은 값으로 강제** 합니다. `-storepass`와 `-keypass`를 다르게 줘도 경고만 뜨고 실제로는
> `-storepass` 값 하나로 통일되니, 아래 `keystore.properties`의 두 값도 반드시 같게 맞춰야
> 합니다.

키스토어 자체와 비밀번호는 **절대 git에 올리면 안 되므로**, 이 프로젝트는 `keyStore/`
폴더 전체를 `.gitignore`에 넣어두고(이미 되어 있음), 그 안에 비밀번호를 담은 파일을
하나 더 둡니다.

**파일 위치**: `keyStore/keystore.properties` (새로 만드는 파일, git에 안 올라감)

```properties
storeFile=release.keystore
storePassword=<storepassword>
keyAlias=trainingmonitor
keyPassword=<keypassword>
```

## A-3. Step 2 — `build.gradle.kts`에 서명/빌드 설정 추가하기

**파일 위치**: `app/build.gradle.kts`

파일 맨 위, `plugins { ... }` 다음에 `keystore.properties`를 읽어오는 코드를 추가합니다.

```kotlin
import java.util.Properties

// 릴리스 서명 정보. keyStore/keystore.properties(git에는 올라가지 않음, .gitignore의 /keyStore/ 참고)에서
// storeFile/storePassword/keyAlias/keyPassword를 읽어온다. 파일이 없으면(=이 저장소를 새로 받은 경우)
// 릴리스 빌드에서만 실패하고 디버그 빌드는 영향받지 않는다.
val keystorePropertiesFile = rootProject.file("keyStore/keystore.properties")
val keystoreProperties = Properties().apply {
    if (keystorePropertiesFile.exists()) {
        keystorePropertiesFile.inputStream().use { load(it) }
    }
}
```

`android { ... }` 블록 안, `compileOptions { ... }` 다음에 서명 설정과 빌드 타입별
서버 주소를 추가합니다.

```kotlin
signingConfigs {
    create("release") {
        if (keystorePropertiesFile.exists()) {
            storeFile = rootProject.file("keyStore/${keystoreProperties["storeFile"]}")
            storePassword = keystoreProperties["storePassword"] as String
            keyAlias = keystoreProperties["keyAlias"] as String
            keyPassword = keystoreProperties["keyPassword"] as String
        }
    }
}

// 사내 테스트용 APK라 릴리스 빌드 시 자동으로 도는 Lint 검사(lintVitalRelease)를 끈다.
// (그대로 두면 Lint가 쓰는 외부 도구를 매번 인터넷에서 받아오다 실패할 수 있다.)
lint {
    checkReleaseBuilds = false
}

buildTypes {
    release {
        signingConfig = signingConfigs.getByName("release")
        isMinifyEnabled = false
        // 폰이 PC와 같은 Wi-Fi(같은 공유기)에 있을 때 독립적으로 접속할 PC의 LAN IP.
        // 네트워크가 바뀌면(PC의 IP가 바뀌면) 이 값도 같이 바꿔서 다시 빌드해야 한다.
        buildConfigField("String", "BASE_URL", "\"http://<PC의 LAN IP>:5133/\"")
    }
}
```

`defaultConfig`의 기존 `BASE_URL`(`http://127.0.0.1:5133/`)은 디버그 빌드용으로 그대로
둡니다. `buildTypes.release`의 `buildConfigField`가 릴리스 빌드에서만 이 값을 덮어씁니다.

### 이 설정이 하는 일

| 코드 | 설명 |
|---|---|
| `Properties().apply { ... load(it) }` | 자바 표준 `Properties` 클래스로 `.properties` 파일(키=값 형식)을 읽습니다. 비밀번호를 소스 코드에 직접 적지 않기 위한 방법입니다. |
| `if (keystorePropertiesFile.exists())` | 이 파일이 없어도(예: 다른 사람이 이 저장소를 새로 클론했을 때) `./gradlew assembleDebug`는 영향받지 않고, `assembleRelease`를 실행할 때만 서명 정보가 없어 실패합니다. |
| `isMinifyEnabled = false` | 코드 축소/난독화(R8)를 끕니다. Play 스토어에 배포할 게 아니라 사내에서 파일로 나눠주는 용도라 굳이 켤 필요가 없고, 켜면 리플렉션을 쓰는 라이브러리가 깨질 수도 있어 불필요한 복잡도를 피했습니다. |
| `buildTypes.release { buildConfigField(...) }` | 같은 이름(`BASE_URL`)의 `buildConfigField`를 빌드 타입에서 다시 선언하면, `defaultConfig`의 값을 그 빌드 타입에서만 덮어씁니다. |

## A-4. Step 3 — 릴리스 APK 빌드하기

```bash
./gradlew assembleRelease
```

빌드가 끝나면 `app/build/outputs/apk/release/app-release.apk`가 생성됩니다. `BUILD
SUCCESSFUL`이 뜨는지 꼭 확인하세요.

## A-5. Step 4 — 설치하고 확인하기

**USB로 연결된 폰에 바로 설치할 때** (테스트 목적):

```bash
adb uninstall com.training.monitor   # 디버그 버전이 이미 깔려 있으면 서명이 달라 필요
adb install app/build/outputs/apk/release/app-release.apk
```

**다른 사람 폰에 파일로 전달할 때**: `app-release.apk` 파일을 카카오톡/USB/이메일 등으로
전달하고, 받는 사람이 파일을 눌러 설치합니다. 안드로이드가 "출처를 알 수 없는 앱" 설치
차단 경고를 띄우면, 설정에서 그 앱(카카오톡, 파일 관리자 등)에 대해 "알 수 없는 앱 설치
허용"을 켜야 합니다.

설치 후 앱을 열고 로그인해서 대원 목록까지 정상적으로 뜨는지 확인합니다. 이때 **폰이
PC와 같은 네트워크(같은 공유기)의 Wi-Fi에 연결돼 있어야** `buildTypes.release`에 적어둔
LAN IP로 접속이 됩니다.

### 트러블슈팅

| 증상 | 원인 | 해결 |
|---|---|---|
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE: ... signatures do not match` | 디버그 서명으로 이미 설치된 앱 위에 릴리스 서명 APK를 덮어 설치하려 함(또는 반대) | `adb uninstall com.training.monitor`로 먼저 지운 뒤 설치 |
| `assembleRelease`가 `lintVitalAnalyzeRelease` 단계에서 인터넷 다운로드 실패로 멈춤 | 릴리스 빌드는 기본적으로 "vital lint" 검사를 먼저 돌리는데, 이 검사가 쓰는 외부 도구를 받다가 실패함(네트워크 문제) | `android { lint { checkReleaseBuilds = false } }`로 릴리스 빌드의 자동 Lint를 꺼둠 |
| 앱은 켜지는데 "서버 연결 실패" | 폰이 PC와 다른 네트워크에 있거나(다른 Wi-Fi, 모바일 데이터), `buildTypes.release`의 `BASE_URL`에 적은 IP가 PC의 실제 IP와 다름(IP가 바뀌었을 수 있음) | 폰에서 `PC의 LAN IP:5133/swagger`를 브라우저로 열어 응답이 오는지 먼저 확인 — 안 되면 네트워크 문제, 되면 앱을 그 IP로 재빌드 |
| 키스토어 비밀번호를 까먹음 | `keyStore/keystore.properties`는 git에 안 올라가므로 PC를 바꾸거나 파일을 지우면 복구 불가 | 키스토어 파일과 비밀번호를 반드시 별도로 백업해 둘 것 (분실 시 새 키로 만들면 기존 설치본 위에 업데이트 설치가 불가능해짐) |

## A-6. PC의 LAN IP를 알아내는 방법

Windows PowerShell에서:

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Select-Object InterfaceAlias, IPAddress
```

여러 개가 나오면(사내망처럼 어댑터 하나에 IP가 여러 개 붙어 있는 경우 등), 폰에서 각
IP로 핑을 보내서 실제로 응답하는 IP를 찾는 게 가장 확실합니다.

```bash
adb shell ping -c 2 <후보 IP>
```

> 폰과 PC가 물리적으로 다른 네트워크(PC는 유선, 폰은 Wi-Fi)여도, 그 둘이 **같은 공유기/스위치에
> 물려 있거나 라우터가 두 네트워크 사이를 라우팅**해주면 통신이 됩니다. 핑으로 직접 확인하는
> 것이 IP 대역만 보고 추측하는 것보다 훨씬 정확합니다.
